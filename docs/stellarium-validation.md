## 3. 빌드와 로딩 제약

고정 커밋은 현재 Windows 작업 폴더와 Docker 조합에서 그대로 빌드되지 않아 실험 vendor에 다음 호환 패치를 적용했다.

- SCons의 asset 생성 호출을 문자열 대신 `python3`, 스크립트 경로 배열로 전달
- Docker의 `/app/tools` 경로를 asset 스크립트 허용 경로에 포함
- Windows CRLF의 `\r`이 생성된 C 문자열에 들어가지 않도록 제외

이 패치는 무시된 vendor 작업 폴더에만 있으며 아직 제품 빌드 패치로 커밋하지 않았다. 운영 자산을 재현하려면 패치 파일 또는 별도 빌드 스크립트를 검토 가능한 형태로 고정해야 한다.

Vite는 `public` 아래의 엔진 JavaScript를 소스 모듈처럼 직접 import하는 것을 막았다. 실험에서는 파일을 fetch한 뒤 Blob module URL로 동적 import해 우회했다. 이 방식은 동작 확인에는 충분하지만 CSP의 `blob:` 허용, 오류 스택·소스맵, Blob URL 해제와 장기 캐시 전략을 함께 검토해야 한다. C14의 제품 어댑터에서는 정적 자산 공급 방식과 CSP를 먼저 정하고 같은 우회를 그대로 복사하지 않는다.

엔진 vendor, JS/WASM, skydata, font와 Dockerfile은 현재 Git에서 제외된다. 따라서 저장소 clone만으로 C05를 즉시 재현할 수 있는 상태는 아니다. 엔진·데이터·폰트의 이용 조건과 소스 제공 방식은 C21, 운영 경로·WASM MIME·캐시는 C22에서 확정한다.

## 4. 제품 구현에 적용할 결론

C05는 현재 좌표·UTC·FOV·대기·별자리의 핵심 연결 가능성을 확인했으므로 제품 개발을 계속할 수 있다. C14에서는 엔진 호출을 `StellariumAdapter` 안에 두고 다음 규칙을 적용한다.

- 위도·경도와 FOV는 deg에서 rad로 변환하고 현재 UTC는 엔진의 `date2MJD`를 사용한다.
- 제품의 밤 진입은 C07의 공개 설정으로 먼저 판정한다. 실험처럼 낮 하늘을 보여주는 경로는 제품 라우트에 포함하지 않는다.
- 별·서양 sky culture·태양·달·NotoSans는 필수 준비 상태로, DSO·은하수는 부분 준비 상태로 구분한다.
- JS/WASM 초기화와 필수 skydata 준비를 나누어 오류와 재시도를 표시한다.
- 자동 천체 추적은 끄고 앱의 현재 UTC를 계속 전달한다. 엔진 내부 시간 진행과 중복시키지 않는다.
- 초기화 중 이탈·반복 진입·탭 숨김에서 listener, animation loop, canvas, Blob URL과 WebGL context를 정리한다.

## 5. 후속 검증

C14~~C17에서 데스크톱 드래그·휠, 모바일 핀치, 20~~120° FOV 제한, 초기 시선 복구, 별자리 토글, 밤 종료와 탭 복귀를 제품 화면에서 검증한다. Android Chrome과 iOS Safari, 반복 진입 메모리, 실제 배포 경로, CSP는 C18~C22의 검증 범위로 남긴다.

천문 정확도는 대표 좌표·UTC에서 엔진 표시와 독립 기준을 비교해야 한다. C05는 값 전달과 렌더링 성공을 확인한 실험이며 별의 방위·고도 수치 정확도까지 증명한 것은 아니다.
