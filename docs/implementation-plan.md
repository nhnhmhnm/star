# 커밋별 구현 계획서

현재는 기획 문서 정리 단계다. 아래는 앞으로 개발할 순서와 **예정 커밋 메시지**이며 실제 구현·커밋·푸시·배포 내역이 아니다. 언어·역할·작업 규칙은 [개발 가이드](./development-guide.md)를 따른다.

## 1. 순서와 원칙

`환경 준비 → 엔진 최소 검증 → 공통 상태·밤 판정 → 메인 세계지도 → 밤하늘 페이지 → 기상·필요 시 API → 품질·출시 준비`

정식 화면은 지도부터 개발한다. 지도에 착수하기 전에 작은 실험 화면으로 핵심 엔진의 데이터 공급·현재 하늘 표시 가능성을 확인한다. 기존 계획의 ‘완성된 하늘 페이지를 먼저 개발’ 순서는 이 문서로 대체한다.

객체지향 경계는 [설계 원칙](./object-oriented-design.md)에 따라 해당 기능 커밋에서 함께 구현한다. 처음부터 모든 인터페이스와 빈 클래스를 만드는 별도 단계는 두지 않는다. 기존 외부 동작을 유지한 구조 변경에만 refactor를 사용한다.

각 행은 기본 커밋 경계다. 한 기능의 의미 있는 테스트와 관련 문서는 그 기능 커밋에 포함하며 실제 변경이 커지면 더 작게 나눈다. 아래의 검증은 향후 수행할 완료 기준이다.

## 2. 환경·핵심 엔진 검증

| ID | 예정 커밋 메시지 | 작업 범위·완료 기준 |
|---|---|---|
| C01 | `chore(repo): 저장소와 패키지 관리 기준 구성` | Git이 없으면 초기화, 웹 Node/npm 버전·ignore·lockfile 기준. API의 Python/uv는 B01에서 준비, 비밀 값 제외 |
| C02 | `chore(web): React와 TypeScript 개발 환경 구성` | frontend의 Vite·CSS 기반, 개발 실행·빌드 가능 |
| C03 | `chore(tooling): 코드 검사와 테스트 환경 구성` | 타입·린트·포맷·단위/컴포넌트 검사 명령, 커밋 제목 규칙 설정 |
| C04 | `build(stellarium): 엔진 공급 방식과 필수 자산 경로 고정` | 커밋·빌드 도구·별/sky culture/폰트 목록과 재현 방법, 로드 경로 확인 |
| C05 | `chore(spike): 현재 하늘과 별자리의 엔진 연동 검증` | frontend/experiments/stellarium에서 좌표·UTC·FOV·대기·별자리·입력 확인, 제품 배포에서 제외 |
| C06 | `docs(stellarium): 엔진 검증 결과와 제약 사항 기록` | 단위·데이터 준비·수명주기·모바일 검증 결과와 남은 제한 기록 |

C05가 막히면 공급 방식과 필수 자산부터 해결한다. 실패한 실험을 기능 완료로 표시하지 않는다. 실험을 유지하지 않는 경우 결과 문서에 재현 절차를 남기고 커밋 범위를 조정한다.

## 3. 앱 기반·메인 세계지도

| ID | 예정 커밋 메시지 | 작업 범위·완료 기준 |
|---|---|---|
| C07 | `feat(night): 현재 좌표의 밤하늘 진입 조건 추가` | 좌표·UTC·단위의 순수 함수 계약, h <= -18° 허용, 경계/오류/날짜변경선 검증 |
| C08 | `feat(web): 지도와 밤하늘 페이지의 기본 구조 추가` | 라우트·공통 상태·기본 레이아웃, 위치 없는 하늘 진입은 지도 안내 |
| C09 | `docs(map): 지도와 검색 제공자 선택 근거 정리` | 지원 범위·한국어 품질·비용·키·표시 조건 확정 기록 |
| C10 | `feat(map): 세계지도 확대와 이동 기능 추가` | MapController와 지도 어댑터, 타일·출처·PC/모바일 조작, 실패 재시도 |
| C11 | `feat(search): 장소 검색과 지도 이동 연결` | PlaceSearchProvider 경계, 결과는 지도 이동·확대만, 선택 해제·응답 순서·오류 |
| C12 | `feat(location): 지도 클릭 좌표 확정과 선택 카드 추가` | 클릭/tap과 제스처 구분, 읽기 전용 좌표·밤 안내·키보드 명시적 선택 |
| C13 | `feat(map): 낮과 박명 밝기 및 동일한 밤 색상 적용` | 현재 태양 기준 밝기, h <= -18° 동일 색/투명도, 지명·도로 가독성과 지리 좌표 정합 |

C09는 제공자와 비용을 결정하는 작업이며 자동 가입·결제를 뜻하지 않는다. C12에서 카드는 관측 가능 여부를 표시하되 실제 하늘 연결은 C14에서 완료한다.

## 4. 밤하늘 상세 페이지

| ID | 예정 커밋 메시지 | 작업 범위·완료 기준 |
|---|---|---|
| C14 | `feat(sky): 선택 위치의 현재 밤하늘 연결` | SkyEngine 계약·StellariumAdapter, 현재 UTC·자산·시선·대기·실패, 첫 프레임 전 밤 재판정 |
| C15 | `feat(sky): 하늘 방향과 확대 조작 추가` | 드래그·휠·핀치·버튼, 20~120° FOV·초기 시선 복구·입력 충돌 |
| C16 | `feat(sky): 별자리 선과 이름 표시 전환 추가` | sky culture 준비 후 독립 토글, 표시 오류·재시도 |
| C17 | `feat(sky): 관측 종료와 탭 복귀 처리 추가` | 매초 밤 재판정, 기준 초과 시 가림·중단, 복귀 현재 UTC와 첫 화면 차단·이탈 정리 |

C14 이후의 중간 개발 상태도 밤 진입은 검사한다. C17이 끝나기 전에는 연속 관측 정책이 완성된 것으로 보지 않는다. 모든 단계에서 사용자 시간 조작 기능은 추가하지 않는다.

## 5. 기상·백엔드 — 채택할 때 진행

지도/검색에 서버가 먼저 필요한 것으로 결정되면 B01~B03을 C09 이후 필요한 위치로 옮긴다. 그렇지 않으면 기상 작업에서 백엔드 필요성을 판단한다. DB·회원 기능은 추가하지 않는다.

| ID | 예정 커밋 메시지 | 작업 범위·완료 기준 |
|---|---|---|
| W01 | `docs(weather): 기상 제공자와 첫 버전 반영 범위 정리` | 요약·구름 채택 범위, 유효 시각·단위·갱신/실패·이용 조건 결정 |
| B01 | `chore(api): Python과 FastAPI 개발 환경 구성` | 필요할 때 backend에 Python·uv·FastAPI·Uvicorn·Ruff·pytest 구성, lockfile·환경 설정·상태 확인 |
| B02 | `feat(api): 외부 데이터 중계와 응답 계약 추가` | Router·Service·Provider 계약과 조립, Pydantic·backend/openapi.json, 외부 응답 정규화·시간 초과·키·CORS·pytest 검증 |
| B03 | `feat(api): 외부 요청 캐시와 호출 제한 추가` | 제공자 정책에 맞는 캐시·요청량 제한·재시도, 임의 외부 URL 중계 금지 |
| W02 | `feat(weather): 관측 위치의 기상 정보 표시` | 직접/중계 응답 연결, 운량·날씨·자료 기준 시각과 출처 표시 |
| W03 | `feat(weather): 기상 갱신과 지연 상태 처리 추가` | 선택 ID·좌표 키·취소/순서, 15분 갱신 제안, 누락·오래된 데이터는 미반영 |
| W04 | `chore(spike): 운량 기반 구름 합성 가능성 검증` | 시선·줌·가림·모바일 프레임·제약 기록, 실험은 제품 배포 제외 |
| W05 | `feat(weather): 운량에 따른 구름과 별 가림 적용` | W04 통과 후만 진행, 별자리 가림·동작 줄이기·맑음/흐림 경향 |

백엔드 언어는 Python + FastAPI로 확정했다. B01 이후부터 B02~B03까지 API 검사도 각 커밋에 함께 수행한다. 백엔드가 필요 없으면 B01~B03을 생략한다. 구름이 첫 버전 범위에서 빠지면 W04~W05를 미구현으로 남긴다. 조건부 작업을 완료한 것처럼 커밋하거나 빈 커밋을 만들지 않는다.

## 6. 품질·출시 준비

| ID | 예정 커밋 메시지 | 작업 범위·완료 기준 |
|---|---|---|
| C18 | `test(e2e): 지도 선택과 실시간 관측 흐름 검증` | 검색→클릭→진입, 낮 차단·경계 종료·탭 복귀·반응형, 기능별 단위 테스트와 별개 |
| C19 | `perf(web): 하늘 자산 로딩과 반복 진입 비용 개선` | 측정으로 확인한 문제만 개선, lazy loading·렌더 비용·누수 전후 결과 |
| C20 | `ci(repo): 변경 사항의 자동 검증 구성` | 웹 타입·린트·테스트·빌드, API 도입 시 uv lock·Ruff·pytest·Python 타입·계약 검사, 외부 API는 모의 응답 |
| C21 | `docs(licenses): 엔진과 외부 데이터의 이용 조건 정리` | 자산 버전·출처·고지·소스 제공 방식, 실제 사용하는 서비스만 기록 |
| C22 | `build(web): 배포 경로와 자산 제공 설정 구성` | 하위 경로·WASM MIME·CORS·캐시, 배포 대상 확정 후 필요한 설정과 검증 |

C19는 측정상 필요할 때 진행하며 불필요한 변경을 만들지 않는다. 버그가 발견되면 해당 목적의 fix 커밋을 추가한다. C22는 배포 준비이며 운영 공개·원격 푸시·병합은 별도 작업이다.

## 7. 커밋별 완료 보고와 문서 관리

개발할 때 각 단위마다 실제 커밋 해시·한글 제목·변경 결과·수행한 검증·남은 제한을 보고한다. 계획에 없던 변경은 이유를 남기고 해당 요구사항에 연결한다. 장기 작업의 상태는 실제 완료·미완료를 구분해서 이 문서에 반영한다.

전체 기능 기준은 [제품 요구사항](./product-requirements.md), 상세 검증은 [테스트 계획](./test-plan.md), 메시지 형식은 [개발 가이드](./development-guide.md)가 기준이다.
