# 결정 및 위험 관리

검토일: 2026-09-09. 사용자 의도로 확정한 정책, 제안한 기술 선택, 향후 검증을 구분한다.

## 확정한 제품 정책

| 항목      | 결정                                                                            |
| --------- | ------------------------------------------------------------------------------- |
| 밤 기준   | 기본값은 태양 중심의 기하 고도 -18° 이하, 백엔드 환경 변수로 변경 가능          |
| 시간      | 현재 시각만 사용, 배속·정지·과거/미래 이동 없음                                 |

| 관측자 핀 | 밤하늘을 실제로 보는 동안만 근사 관측 위치와 닉네임 공개, 같은 셀은 집계        |

이전 검토의 낮 진입 허용·배속·직접 좌표 입력·다음 밤 시각 이동안은 폐기한다. 감상 중 밤 조건 종료 시 하늘을 가리고 재선택을 안내하는 UX를 설계했다.

## 채택한 기획안

### 현재 하늘과 대기

지평선 기준 시선을 고정하고 자동 천체 추적을 해제한다. 초기 북쪽 0°·고도 45°·FOV 70°, 줌 20~120°를 제품 설정으로 둔다. 대기는 켜 두고 균일한 검정 배경을 강제하지 않는다.

공식 대기 소스는 태양·달의 위치와 밝기, 대기 및 광공해 설정 등을 사용한다. 실제 좌표의 광공해·날씨가 자동 조회되는 것과는 다르다. [대기 소스](https://github.com/Stellarium/stellarium-web-engine/blob/master/src/modules/atmosphere.c)

### 지도 시각 표현과 진입 판정

지도 밝기는 현재 태양 고도에 따른 연속적인 안내다. 가장 밝은 중심은 낮의 태양 방향에 대응하고 대한민국이 정오 부근이면 한국이 포함된 낮 영역이 밝게 느껴지도록 한다. 화면의 클릭 위치를 빛의 중심으로 바꾸지 않는다.

사용자 결정에 따라 기본 h <= -18°는 모두 같은 밤 색상·투명도로 고정하며, 밤 내부의 추가 밝기 차이는 주지 않는다. 환경 설정으로 경계를 바꾸면 동일 밤 색상의 경계도 같은 값을 따른다. UX상 밤을 완전히 검게 만들지 않는다. 별도로 관측 가능 경계·범례를 제공하고 최종 클릭 좌표에서 직접 판정한다. 밝은 정도를 관측 가능 여부의 유일한 신호로 사용하지 않는다.

### 닉네임과 실시간 관측자 핀

닉네임은 sessionStorage와 임시 서버 세션에만 두고 중복을 허용한다. 지도에는 기기 GPS가 아니라 사용자가 선택해 현재 감상 중인 관측 위치를 기본 0.25° 격자로 흐리게 표시한다. 정확한 클릭 좌표와 관측 이력은 영구 저장하지 않는다. 한 셀의 여러 사용자는 인원수 핀으로 집계하고 상세에서 닉네임을 보여준다.

실시간 상태는 Python + FastAPI의 WebSocket과 60초 TTL 메모리 저장소로 시작한다. 이 기능 때문에 백엔드 도입 시점을 앱 기반 단계로 앞당긴다. 서버 장애는 관측자 핀만 unavailable로 만들고 지도 탐색과 하늘 감상은 유지한다. [상세 기획](./presence-and-chat.md)

### 기상은 추가 검토 범위

기상 요약과 운량 기반 구름을 제안하되 형상·불투명도·바람·가림은 별도 시각화 설계다. 실황 구름 복원이라고 약속하지 않는다. [기상 반영 검토안](./weather-integration.md)

## 공급자와 운영 결정

돈을 쓰지 않는 개인 로컬호스트 프로젝트로 시작한다. 지도 기본 구현은 MapLibre GL JS와 무료 개발용 지도 스타일/타일, 그리고 토큰 없는 정적 세계지도 fallback을 우선한다. 외부 지도·검색 API는 무료 조건과 호출 제한이 명확하고, 초과 과금이 발생하지 않는 범위에서만 선택한다. [지도·검색 제공자 선택 근거](./map-provider-decision.md)

Google Maps + Places는 검색 품질 대안이지만 결제 활성화와 SKU별 과금 구조가 있어 현재 기본 공급자에서 제외한다. Google 검색 데이터를 다른 지도와 조합할 때도 표시 제한을 검토해야 한다. [사용·과금](https://developers.google.com/maps/documentation/javascript/usage-and-billing), [Places 정책](https://developers.google.com/maps/documentation/places/web-service/policies)

Leaflet을 선택하면 별도의 타일·검색 공급자가 필요하다. 공개 OSM 타일 서버를 무제한 운영 인프라로 가정하지 않는다. 공개 Nominatim은 자동완성을 허용하지 않고 앱 전체 호출 제한이 있어 현재 검색 UX의 기본 공급자로 채택하지 않는다. [OSM 타일 정책](https://operations.osmfoundation.org/policies/tiles/), [Nominatim 정책](https://operations.osmfoundation.org/policies/nominatim/)

Open-Meteo는 기상 후보이며 무료 API의 비상업 조건·제한과 상업용 제공 방식, 귀속 표기를 확인한다. 현재 요청·키 발급·계약은 수행하지 않는다. [공식 이용 안내](https://open-meteo.com/en/pricing)

## 엔진·데이터 이용 조건

엔진 저장소의 AGPL v3 원문과 소스 헤더의 상용 라이선스 대안 언급을 확인했다. 공개 방식에 따른 소스 제공·고지·빌드 재현 방식은 개발 전에 결정한다. 구체적인 상용 계약 조건은 미확인이다. [라이선스](https://github.com/Stellarium/stellarium-web-engine/blob/master/LICENSE-AGPL-3.0.txt), [소스 헤더](https://github.com/Stellarium/stellarium-web-engine/blob/master/src/observer.h)

별·sky culture·그림·폰트·외부 CDN의 조건은 엔진 코드와 별도로 기록한다. 엔진의 라이선스만으로 모든 데이터의 운영 이용이 허용된다고 가정하지 않는다.

## 남은 결정

지도·검색은 비용 0원 원칙을 확정했으며, 구체적인 무료 타일·검색 데이터와 fallback 품질은 C10~C11에서 검증한다. 엔진 자산의 운영 공급 방식, 앱 공개 방식, 기상 요약/구름의 첫 버전 포함 범위, 지원 기기와 한글화 깊이, 공개 전 닉네임 운영 정책은 향후 확정한다. 밤 기준의 기본값 -18°와 환경 설정 방식은 확정됐으므로 다시 미결정 항목으로 두지 않는다.

발전 방향은 ‘현재 다른 곳의 밤을 함께 본다’는 목적을 유지한다. 기상 안내·별자리 설명·현재 위치로 지도 이동·현재 밤 지역 공유·동시 관측 비교를 검토하며 시간 이동 기능은 추가하지 않는다. 소셜 로그인과 같은 지역 관측자 채팅은 후속 후보지만, 채팅 지역 단위·운영·보관 정책을 정하기 전에는 구현하지 않는다.

## 개발 언어·커밋 방식 결정 — 2026-09-08

- 프론트엔드: TypeScript + React + Vite
- 백엔드: **사용자 선택으로 Python + FastAPI 확정**, 공개 설정·presence를 위해 앱 기반 단계에서 도입
- Java + Spring Boot도 가능하지만 이번 구현은 Python을 사용한다. 기존 TypeScript 서버 통일안은 대체한다.
- 외부 API는 HTTP·JSON·OpenAPI 계약으로 연결한다. Python과 TypeScript의 런타임·의존성은 각각 관리한다.
- 엔진 최소 검증 후 FastAPI·공개 설정 → 닉네임 → 메인 지도·관측자 핀 → 밤하늘 → 기상 순서로 진행한다.
- 개발은 목적별 구현·검증·커밋으로 진행하며 타입/scope는 영어, 설명·본문은 한글로 작성한다.

언어 선택은 미결정에서 제외한다. API가 실제로 필요한 시점·외부 공급자·비용·구름 범위는 기존 미결정을 유지한다. [개발 가이드](./development-guide.md), [커밋 계획](./implementation-plan.md)

## 유지보수 설계 원칙 — 2026-09-08

역할별 계약·합성·의존성 주입으로 지도·검색·엔진·기상 공급자의 변경 범위를 제한한다. 상태·자원 관리는 객체에, 순수 계산은 함수에, 화면은 React 함수 컴포넌트에 둔다. Python + FastAPI 선택은 유지한다.

공급자 교체에는 단위·오류·사용 조건 검증이 필요하므로 인터페이스만으로 자동 교체가 보장된다고 설명하지 않는다. 필요 없는 추상 계층·DB Repository·만능 서비스는 추가하지 않는다. [객체지향 설계](./object-oriented-design.md)
